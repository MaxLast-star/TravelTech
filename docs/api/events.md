# Каталог доменных событий

Каталог собран из message events в BPMN: если события нет ни в одной диаграмме и ни в
одном требовании, его нет и здесь. Для архитектора это список каналов шины, для
API-агента — основа AsyncAPI, для дата-агента — перечень того, что пишется в хранилище
статусов и в аудит.

Синхронные вызовы внешних систем сюда не входят — почему, сказано в разделе
[Что событием не является](#что-событием-не-является).

## Соглашения

Имя — `<домен>.<событие>.v<N>`. Версия входит в имя канала: несовместимое изменение
схемы выпускается как `v2`, `v1` живёт, пока на нём есть потребители.

Доставка — at-least-once. Порядок гарантируется только внутри партиции, то есть внутри
одного значения ключа. Ключ партиционирования выбирается по тому, в пределах чего порядок
обязан соблюдаться, а не по тому, что удобно писать.

Времена в конверте два: `event_at` — когда событие произошло у источника, `ingest_at` —
когда его принял приёмник. Решения принимаются по `event_at`; разность двух времён и есть
измеримый лаг из НФТ. Оба в UTC.

Обязательные поля конверта: `event_id`, `event_type`, `event_at`, `ingest_at`,
`partition_key`, `producer`, `trace_id`, `schema_version`. Полезная нагрузка — в `data`.

## Приём статусов и детекция

| Событие | Продюсер | Ключ партиционирования | Назначение |
|---|---|---|---|
| `flight.status.received.v1` | Адаптер источников статусов | `flight_key` — номер рейса и дата вылета в UTC | Сырой статус от провайдера, перевозчика или разбора письма, до дедупликации и до оценки достоверности. Потребитель — сервис детекции |
| `disruption.detected.v1` | Сервис детекции | `booking_id` | Открыт сбой по бронированию: тип, класс влияния, ссылка на исходный статус. Запускает экземпляр P-01 (`P-01.S1`). При повторном сбое несёт `supersedes_disruption_id` (`FR-DET-03`) |

## Уведомление и решение

| Событие | Продюсер | Ключ партиционирования | Назначение |
|---|---|---|---|
| `disruption.notified.v1` | Оркестратор сбоя | `disruption_id` | План исполним, вариантов не предлагается — путешественник информируется и сбой закрывается (`P-01.E1`) |
| `decision.requested.v1` | Оркестратор сбоя | `disruption_id` | Запрос выбора альтернативы ответственному за бронирование с перечнем годных вариантов и сроком ответа (`P-01.M2`, `FR-NTF-03`) |
| `decision.reminded.v1` | Оркестратор сбоя | `disruption_id` | Ответа нет 10 минут — повтор следующим каналом лестницы (`P-01.E4`, `FR-NTF-02`) |
| `notification.delivery.reported.v1` | Адаптер канала доставки | `notification_id` | Статус доставки от провайдера канала. Факт отправки подтверждением не считается — переход к следующему каналу происходит по этому событию или по его отсутствию (`FR-NTF-02`) |
| `decision.submitted.v1` | Шлюз `C-API` | `disruption_id` | Выбор альтернативы от путешественника или от организатора с действующим мандатом. Корреляция в движке по `disruption_id`. Пока ack-окно открыто, сообщение ловит `P-01.T3`; после закрытия — событийный подпроцесс `P-01.SUB2` (`FR-DEC-01`, `FR-DEC-05`) |
| `disruption.resolved.v1` | Оркестратор сбоя | `disruption_id` | Решение применено, билет выпущен, план обновлён (`P-01.M3`) |

## План поездки

| Событие | Продюсер | Ключ партиционирования | Назначение |
|---|---|---|---|
| `plan.updated.v1` | Сервис плана поездки | `trip_id` | Изменение опубликовано участникам, которых оно затрагивает. Несёт номер версии плана (`FR-PLN-01`, `FR-NTF-05`) |
| `trip.completed.v1` | Сервис плана поездки | `trip_id` | Последний сегмент выполнен. Запускает отсчёт срока удержания паспортных данных (`P-04.S1`) |

| Событие | Продюсер | Ключ партиционирования | Назначение |
|---|---|---|---|
| `pii.purge.mismatch.v1` | Планировщик удержания ПДн | `traveller_id` | После прогона удаления осталась запись с истёкшим TTL. Алерт в наблюдаемость, потребитель — дежурный (`P-04.M1`, `NFR-COMP`) |

## Почему такие ключи

**Сырой статус партиционируется по рейсу, а не по бронированию.** Статус принадлежит
рейсу; один рейс — сотни бронирований. Ключ по бронированию заставил бы размножать одно
событие на все затронутые брони ещё до дедупликации, а порядок нужен ровно между
статусами одного рейса: отмена, пришедшая раньше задержки по `event_at`, не должна
обгонять её в обработке.

**Сбой партиционируется по бронированию.** `NFR-SCAL-02` требует строгого порядка в
пределах бронирования, и это самое узкое место: два конкурирующих статуса по одной броне
обязаны попасть в одну партицию, иначе `FR-DET-03` — обновить открытый сбой, а не создать
второй — выполняется как гонка. `disruption_id` в момент публикации ещё не существует,
поэтому ключ именно `booking_id`.

**Переписка по сбою партиционируется по сбою.** Запрос решения, напоминание и уведомление
о применённом решении обязаны прийти в этом порядке, иначе путешественник получит
напоминание раньше запроса. Разные сбои одного человека независимы и обрабатываются
параллельно.

**План и поездка — по поездке.** Групповая поездка обновляется как целое, порядок версий
плана значим. Участники между разными поездками не связаны.

## Повторная доставка

Доставка at-least-once, значит каждый потребитель идемпотентен. Ключ идемпотентности —
не ключ партиционирования.

| Событие | Ключ идемпотентности | Поведение при повторе |
|---|---|---|
| `flight.status.received.v1` | `source`, `flight_key`, `event_at`, тип статуса | Дубль отбрасывается. Тот же статус от источника с более высоким рангом достоверности обновляет состояние рейса, но нового сбоя не открывает |
| `disruption.detected.v1` | `disruption_id` | Повтор не создаёт второй экземпляр процесса: корреляция по `booking_id` попадает в уже запущенный |
| `decision.requested.v1`, `decision.reminded.v1`, `disruption.notified.v1`, `disruption.resolved.v1` | `notification_id` | Повторная публикация не порождает второе сообщение пользователю. По одному сбою активно не более одного уведомления, новое заменяет предыдущее (`FR-NTF-01`) |
| `notification.delivery.reported.v1` | `notification_id`, `channel`, `status` | Последний статус по каналу выигрывает, история сохраняется |
| `decision.submitted.v1` | `disruption_id`, `decision_id` | Первый выигрывает. Ответ после закрытия ack-окна не отменяет применённое решение — система сообщает о принятом и предлагает начать новый выбор (`FR-DEC-05`) |
| `plan.updated.v1` | `trip_id`, `plan_version` | Версия не выше текущей игнорируется |
| `trip.completed.v1` | `trip_id` | Повтор не сдвигает уже рассчитанный срок удержания |
| `pii.purge.mismatch.v1` | `traveller_id`, `purge_run_id` | Алерт по одному прогону поднимается один раз |

## Что событием не является

Обращения к провайдеру бронирования, справочнику ограничений, платёжному шлюзу и
поставщикам наземных услуг в P-02 и P-03 — синхронные вызовы «запрос — ответ». У них нет
ключа партиционирования, нет повторной доставки и нет потребителей на шине, поэтому в
AsyncAPI они не попадают и в этом каталоге их нет. В диаграммах они нарисованы message
flow с обычными подписями («Запрос альтернатив», «Результат авторизации»), а не именами
событий: так каталог не заполняется записями без ключа партиционирования и без
семантики повтора.

Идемпотентность у этих вызовов своя и живёт в синхронном контракте: выпуск билета
защищён ключом операции, повторный вызов с тем же ключом не выпускает второй билет
(`FR-REB-01`).

## Повторный сбой

Отдельного события для повторного сбоя нет и не нужно. По `FR-DET-03` статус, поступивший
после применённого решения и делающий это решение неисполнимым, открывает новый сбой,
связанный с исходным. Это обычный `disruption.detected.v1` с заполненным
`supersedes_disruption_id`, а не отдельный канал.
