# TravelTech: управление сбоями рейсов

Проектное решение по кейсу «Альфред, друг Бэтмена». Система следит за статусами рейсов
по активным бронированиям, сама обнаруживает сбой, оценивает, что именно сломалось в
плане поездки, подбирает применимые альтернативы и доводит решение до конца — даже если
путешественник в этот момент недоступен.

## Задача

Человек купил поездку из нескольких сегментов: перелёт со стыковкой, трансфер, отель,
оплаченная экскурсия первого дня. Рейс задержали на четыре часа. Перевозчик знает только
про свой сегмент и сообщает о нём с опозданием; про то, что вместе с рейсом рушится
стыковка, трансфер и невозвратная экскурсия, не знает никто, кроме сервиса.

Задание добавляет три условия, каждое из которых меняет конструкцию решения:

- **данные о рейсах приходят с задержкой** и противоречат друг другу;
- **путешественник может быть оффлайн** в тот момент, когда решение нужно принять;
- **альтернативы ограничены** багажом, визами и таймзонами.

Плюс постскриптум: паспортные данные нельзя хранить дольше, чем нужно для поездки.

## Как это решено

Сценарий идёт по конвейеру из шести стадий. Инициирует его не человек, а событие
провайдера — это главное следствие постановки, из которого вытекает всё остальное.

| Стадия | Контейнер | Ключевое решение |
|---|---|---|
| Приём статусов | `C-INGEST` | Три типа источников с рангом достоверности, время события и время приёма хранятся отдельно |
| Детекция | `C-DETECT` | Статусы накапливаются, а прежние не переписываются. Порог свежести переводит рейс в неопределённость, если источник замолчал |
| Оценка влияния | `C-ORCH-IMPACT` | Разбор по всему плану: стыковки, трансферы, отели, активности, затронутые участники поимённо |
| Подбор альтернатив | `C-ALT` | Проверки MCT, багажа, визы и таймзон — отдельные шаги до показа вариантов, результат каждой сохраняется с причиной |
| Решение | `C-ORCH-DECISION`, `C-NOTIFY` | Лестница каналов, ack-окно, авто-политика по таблице решений при молчании |
| Перебронирование | `C-REBOOK`, `C-PLAN` | Сага с компенсациями и явной точкой невозврата, затем перестроение плана |

Паспортные данные вынесены из этого конвейера в отдельный контур — `C-PII`, `C-RETENT`,
`C-VAULT` — со своим хранилищем, своими правами и своим сроком жизни.

## Три решения, определившие остальное

**Молчание человека — штатный исход, а не ошибка.** Уведомление идёт по лестнице
каналов, ack-окно отсчитывается от подтверждения доставки, по его истечении решение
принимает заранее заданное правило. У сбоя ровно три выхода, и ни один из них не
зависит от того, ответил человек или нет. Обоснование — [ADR-04](/architecture/adr).

**Состояние процесса и данные маршрута принадлежат разным сервисам.** Оркестратор знает,
где сейчас сбой и кто отвечает за решение; сервис плана владеет сегментами и версиями
маршрута. У каждой схемы данных ровно один сервис-писатель. Обоснование —
[ADR-05](/architecture/adr).

**Паспортные данные живут в отдельном контуре, а не шифрованным полем в общей базе.**
Шифрование поля закрывает чтение дампа и не даёт ни отдельного срока жизни, ни контроля
доступа, ни доказательства физического удаления. Контур даёт все три, и это проверяемо
числами. Обоснование — [ADR-03](/architecture/adr).

## Идентификаторы

Одна схема имён на все артефакты: BPMN, C4, ERD, спецификации и матрица ссылаются
друг на друга этими идентификаторами.

| Сущность | Формат | Пример |
|---|---|---|
| Функциональное требование | `FR-<ДОМЕН>-<NN>` | `FR-ALT-03` |
| Нефункциональное требование | `NFR-<КАТ>-<NN>` | `NFR-PERF-01` |
| Процесс и шаг процесса | `P-<NN>`, `P-<NN>.T<n>` | `P-01.T4` |
| Контейнер и компонент | `C-<ИМЯ>` | `C-ORCH` |
| Критерий приёмки | `AC-<ID требования>-<n>` | `AC-ALT-03-1` |
| Событие шины | `<домен>.<событие>.v<N>` | `disruption.detected.v1` |
| Запись журнала решений | `ADR-<NN>` | `ADR-03` |

Термины употребляются строго по [глоссарию](/context/glossary): одно понятие — одно
слово во всех документах.
