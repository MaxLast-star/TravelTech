# Границы и допущения

Задание сужено до управления сбоями рейсов. Остальные процессы сервиса —
поиск, бронирование, рекомендации, обратная связь — существуют как контекст:
они порождают данные, на которые опирается сценарий сбоя, но предметом
проектирования не являются.

## В скоупе

| Область | Что проектируется |
|---|---|
| Приём статусов | Приём статусов рейсов из нескольких разнородных источников, приведение к общей модели, дедупликация, разрешение противоречий |
| Детекция | Автоматическое обнаружение задержки, отмены, смены терминала или борта, misconnect |
| Оценка влияния | Разбор последствий сбоя по всему плану поездки: стыковки, трансферы, заезды в отель, активности |
| Альтернативы | Подбор и ранжирование альтернативных рейсов, проверка каждого на MCT, багажный тариф, транзитную визу, таймзоны и разницу тарифа |
| Уведомления | Лестница каналов, ack-окно, повторные попытки, оффлайн-путешественник |
| Решение | Выбор пользователем или организатором, авто-политика по истечении ack-окна |
| Перебронирование | Выпуск нового билета через провайдера, компенсация при неуспехе, расчёт разницы тарифа, инициация доплаты и возврата |
| План поездки | Обновление плана после перебронирования: сдвиг или отмена зависимых бронирований, перерасчёт временной шкалы |
| Групповые поездки | Роли организатора и участника, решение за группу, раздельные и общие уведомления |
| Паспортные данные | Отдельный контур хранения, TTL, физическое удаление, аудит доступа |
| Отказоустойчивость | Поведение при недоступности провайдеров статусов, провайдера бронирования, платёжного шлюза и каналов доставки |

## Вне скоупа

| Область | Почему вне |
|---|---|
| Первичный поиск и покупка билетов, отелей, трансферов | Существующий процесс сервиса. Используется как источник бронирований и не моделируется: считается существующим на момент старта `P-01` |
| Персонализированные рекомендации и подбор активностей | Не участвует в сценарии сбоя |
| Обратная связь по поездке | Отдельный процесс сервиса |
| Подбор нового отеля или активности взамен сорванных | Система отменяет и сдвигает существующие бронирования, но не подбирает замену: это возврат в процесс бронирования |
| Проведение платежа и хранение платёжных реквизитов | Делегируется платёжному шлюзу. Система хранит идентификатор транзакции и сумму, не реквизиты |
| Выдача виз, проверка подлинности документов | Система сверяет данные документа со справочником визовых правил, юридического решения не принимает |
| Регистрация на рейс, посадочные талоны | Зона перевозчика |
| Наземные сбои: поезда, автобусы, паромы | Задание про рейсы. Модель расширяема, но требований на это нет |
| Тарификация и биллинг самого сервиса | Существующая подсистема |

## Допущения

Ни одно из этих утверждений в условии кейса не задано. Каждое принято, чтобы получить
проверяемые требования, и подлежит подтверждению у заказчика.

| Допущение | Что ломается, если неверно |
|---|---|
| Статусы рейсов приходят из трёх источников: агрегатор статусов по подписке, push-уведомления перевозчика или GDS, служебные рассылки перевозчика на почту | Домен `ING` упрощается до одного источника, дедупликация и разрешение конфликтов теряют смысл |
| Источники противоречат друг другу и приходят вне порядка. Достоверность источников ранжируется: push перевозчика выше агрегатора, агрегатор выше почты | Правило разрешения конфликтов надо задавать иначе |
| У сервиса есть договор с провайдером бронирования, позволяющий выпускать involuntary rebooking по PNR без участия оператора | Домен `REB` сводится к подготовке варианта и передаче в поддержку |
| Перевозчик при отмене по своей вине несёт обязательство перебронировать бесплатно. Разница тарифа возникает, когда путешественник выбирает вариант вне этого обязательства | Модель денег в `REB` строится по-другому |
| Справочники визовых правил, MCT по аэропортам и багажных норм доступны как внешний сервис с суточной актуальностью | Проверки ограничений становятся ручными, авто-разрешение недостижимо |
| Каналы доставки: push в приложение, SMS, электронная почта, мессенджер. Порядок задаётся лестницей каналов | Домен `NTF` перестраивается |
| Сервис работает по 152-ФЗ, паспортные данные — персональные данные субъектов, находящихся на территории РФ | Комплаенс-требования `NFR-COMP` меняются на другую юрисдикцию |
| Масштаб: до 500 тыс. активных бронирований на перелёты одновременно, пик сбоев — до 5 тыс. затронутых бронирований в час при массовой отмене | Числа в `NFR-SCAL` пересчитываются |

## Ограничения

Условия, которые система не выбирает и обязана принять как данность.

| Ограничение | Следствие для проектирования |
|---|---|
| Данные о рейсах приходят с задержкой | Время события и время приёма — разные величины, обе хранятся. Решения принимаются по времени события, свежесть контролируется отдельно |
| Путешественник может быть оффлайн | Нельзя строить процесс на синхронном ответе пользователя. Обязательны ack-окно и авто-политика |
| Альтернатива ограничена багажом, визой и таймзоной | Проверка ограничений — отдельный обязательный шаг до показа вариантов, а не фильтр в UI |
| Паспортные данные нельзя хранить дольше, чем нужно для поездки | ПДн в отдельном контуре с TTL и физическим удалением. Шифрование в общей базе требование не закрывает |
| Внешние API отказывают и ограничивают частоту запросов | Деградация вместо отказа: система продолжает работать на оставшихся источниках и сообщает о снижении полноты |
| Международные форматы: несколько таймзон в одном плане, переход через полночь и через дату | Хранение в UTC с отдельным полем таймзоны, отображение в локальном времени точки события |
| Групповая поездка — норма, а не исключение | Решение по сбою имеет владельца и аудиторию, это разные роли |
