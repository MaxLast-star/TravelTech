# P-01. Обработка сбоя рейса

Основной процесс решения. Начинается не с действия человека, а с события провайдера,
и обязан завершиться даже если человек не ответит ни разу.

<BpmnViewer file="/bpmn/p01-disruption.bpmn" />

## Триггер

Сообщение `disruption.detected.v1` от сервиса детекции. Один экземпляр процесса — один
сбой по одному бронированию. Повторный статус того же типа по открытому сбою нового
экземпляра не создаёт: корреляция идёт по `booking_id` (`FR-DET-03`).

## Участники

| Пул | Вид | Роль |
|---|---|---|
| Сервис детекции сбоя | Свёрнутый | Публикует `disruption.detected.v1`. Внутренняя механика приёма и дедупликации статусов — за границей процесса |
| TravelTech IROPS. Обработка сбоя рейса | Развёрнутый | Оркестратор. Здесь же работает оператор поддержки — консоль оператора часть системы, отдельным пулом он не вынесен |
| Путешественник | Свёрнутый | Получает уведомления, возвращает выбор. Свёрнут потому, что происходящее на его стороне система не знает и знать не должна |

## Шаги

| ID | Задача | Тип | Исполнитель | Требование |
|---|---|---|---|---|
| `P-01.S1` | Сбой детектирован | Message start | Сервис детекции | `FR-DET-01` |
| `P-01.T1` | Оценить влияние на план поездки | Service task | Оркестратор | `FR-IMP-01` |
| `P-01.G1` | План исполним? | XOR | — | `FR-IMP-01` |
| `P-01.E1` | Путешественник проинформирован | Message end | Оркестратор → Путешественник | `FR-NTF-01`, `FR-NTF-03` |
| `P-01.T2` | Подобрать альтернативы (P-02) | Call activity | Оркестратор | `FR-ALT-01` |
| `P-01.G2` | Есть годные варианты? | XOR | — | `FR-ALT-07` |
| `P-01.M2` | Запросить решение у ответственного | Message throw | Оркестратор → Путешественник | `FR-DEC-01`, `FR-GRP-02` |
| `P-01.T3` | Ожидать выбор альтернативы | Receive task | Путешественник или организатор | `FR-DEC-01` |
| `P-01.B1` | Ack-окно 20 минут | Boundary timer, прерывающий | — | `FR-DEC-02` |
| `P-01.B2` | Напоминание через 10 минут | Boundary timer, непрерывающий | — | `FR-NTF-02` |
| `P-01.E4` | Напоминание отправлено | Message end | Оркестратор → Путешественник | `FR-NTF-02` |
| `P-01.T4` | Применить авто-политику | Business rule task, DMN `auto-rebooking-policy` | Оркестратор | `FR-DEC-02`, `FR-DEC-03` |
| `P-01.G4` | Исход авто-политики | XOR | — | `FR-DEC-02` |
| `P-01.T5` | Перебронировать (P-03) | Call activity | Оркестратор | `FR-REB-01` |
| `P-01.B3` | Перебронирование не выполнено | Boundary error | — | `FR-REB-03` |
| `P-01.M3` | Уведомить о применённом решении | Message throw | Оркестратор → Путешественник | `FR-NTF-04`, `FR-PLN-01` |
| `P-01.T6` | Разобрать сбой вручную | User task, группа `support` | Оператор поддержки | `FR-DEC-04` |

| `P-01.E3` | Сбой закрыт оператором | End | — | `FR-DEC-04` |

Два события могут прийти в любой момент, пока экземпляр жив, и обрабатываются
событийными подпроцессами. Оба непрерывающие: основной ход процесса продолжается.

| ID | Подпроцесс и его шаги | Требование |
|---|---|---|
| `P-01.SUB1` | Повторный сбой во время обработки: `P-01.S3` ловит `disruption.detected.v1` по тому же бронированию, `P-01.T7` переоценивает влияние и обновляет открытый сбой, `P-01.E5` завершает ветку | `FR-DET-03` |
| `P-01.SUB2` | Ответ после закрытия ack-окна: `P-01.S4` ловит `decision.submitted.v1`, `P-01.T8` фиксирует поздний ответ вместе с основанием применённого решения, `P-01.M4` сообщает о принятом и предлагает начать новый выбор, `P-01.E6` завершает ветку | `FR-DEC-05` |

## События

| Сообщение | Направление | Элемент |
|---|---|---|
| `disruption.detected.v1` | Детекция → система | `P-01.S1`, `P-01.S3` |
| `disruption.notified.v1` | Система → путешественник | `P-01.E1` |
| `decision.requested.v1` | Система → путешественник | `P-01.M2` |
| `decision.reminded.v1` | Система → путешественник | `P-01.E4` |
| `decision.submitted.v1` | Путешественник → система | `P-01.T3`, `P-01.S4` |
| `disruption.resolved.v1` | Система → путешественник | `P-01.M3` |

Ключи партиционирования и поведение при повторной доставке — в
[каталоге событий](/api/events).

## Развилки

**План исполним.** Смена терминала, выхода или борта план не ломает. Путешественник
информируется одним сообщением, вариантов ему не предлагают, сбой закрывается.

**Годных вариантов нет.** P-02 вернул пустой список — либо рейсов нет, либо все отсеклись
на жёстких ограничениях. Ветка идёт прямо на эскалацию, минуя запрос решения: спрашивать
не о чем.

**Кому адресован запрос.** Одна точка `P-01.M2` «Запросить решение у ответственного».
Ответственный определяется мандатом: организатор с действующим мандатом либо сам
путешественник (`FR-GRP-02`). Разводить это на две ветки в диаграмме смысла нет — шаги
и сроки одинаковые, отличается только адресат.

## Исключения и таймауты

| Ситуация | Обработка | Требование |
|---|---|---|
| Ответа нет 10 минут | `P-01.B2`, непрерывающий таймер: уходит напоминание следующим каналом лестницы, ожидание продолжается | `FR-NTF-02` |
| Ответа нет 20 минут | `P-01.B1`, прерывающий таймер: ожидание снимается, включается авто-политика | `FR-DEC-02` |
| Авто-политика вернула `wait` | Возврат на ожидание, второе окно | `FR-DEC-02` |
| Авто-политика вернула `escalate` | Эскалация оператору вместе с историей сбоя и перечнем отклонённых вариантов | `FR-DEC-03`, `FR-DEC-04` |
| Перебронирование не выполнено | `P-01.B3`, граничная ошибка `REBOOKING_FAILED` от P-03 после отката саги. Эскалация оператору | `FR-REB-03` |
| Ответ пришёл после закрытия окна | Применённое решение не отменяется, система сообщает о принятом и предлагает начать новый выбор | `FR-DEC-05` |

Отдельного канала для позднего ответа нет: приходит тот же `decision.submitted.v1`,
разница только в том, кто его ловит. Пока открыт `P-01.T3` — это выбор, после закрытия
ack-окна — событийный подпроцесс `P-01.SUB2`. Заводить второе имя события ради этого
значило бы описывать состояние получателя в имени сообщения.

Ack-окно 20 минут и напоминание через 10 — рабочие значения, проверяются долей ответов,
полученных до истечения окна. Отсчёт начинается с момента сдачи уведомления в первый
канал лестницы, а не с момента детекции сбоя (`FR-DEC-02`).

## Три выхода

Процесс завершается ровно тремя способами: `P-01.E1` — информированием, `P-01.E2` —
применённым решением, `P-01.E3` — разбором оператора. Четвёртого нет: сбой не может
остаться открытым из-за молчания путешественника, в этом и смысл пары «ack-окно плюс
авто-политика».

`P-01.E4` выходом процесса не является — это завершение непрерывающей ветки напоминания,
основное ожидание в этот момент продолжается.
