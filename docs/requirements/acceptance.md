# Критерии приёмки

Идентификатор: `AC-<ID требования без префикса FR>-<n>`, например `AC-ALT-04-1`
для `FR-ALT-04`. Формат — Gherkin.

По одному сценарию на требование: выбран тот случай, который доказывает правило.
Числовые значения взяты из [нефункциональных требований](./non-functional.md)
и здесь не переопределяются.

## ING. Приём статусов рейсов

**AC-ING-01-1**

```
Сценарий: Статус принят от источника любого типа
  Дано бронирование с сегментом SU1234 и подписка на статусы
  Когда агрегатор, push перевозчика или служебная рассылка сообщает об изменении вылета
  Тогда статус сохранён в единой модели с указанием источника и его ранга
  И сообщение, из которого статус извлечь не удалось, направлено оператору поддержки
```

**AC-ING-02-1**

```
Сценарий: Обе отметки времени зафиксированы, прежний статус сохранён
  Дано у сегмента есть статус со временем события 09:00 UTC
  Когда в 10:07 UTC принят статус со временем события 10:00 UTC
  Тогда у нового статуса время события 10:00 UTC и время приёма 10:07 UTC
  И запись со временем события 09:00 UTC не изменена и не удалена
```

**AC-ING-03-1**

```
Сценарий: Текущее состояние выбирается по рангу и времени события
  Дано текущий статус "задержка 40 минут" получен от агрегатора
  Когда push перевозчика сообщает "рейс отменён", а агрегатор повторяет прежнее сообщение
  Тогда текущим статусом становится "рейс отменён"
  И повторное сообщение не создаёт статуса и не порождает детекции
  И факт противоречия сохранён с указанием обоих источников
```

**AC-ING-04-1**

```
Сценарий: Устаревший статус переводит сегмент в неопределённость
  Дано последний статус сегмента получен 20 минут назад при пороге свежести 15 минут
  Когда система оценивает состояние сегмента
  Тогда сегмент находится в состоянии неопределённости
```

## DET. Детекция сбоя

**AC-DET-01-1**

```
Сценарий: Задержка создаёт сбой, смена терминала — нет
  Дано сегмент с плановым вылетом 12:00 UTC
  Когда принят статус с вылетом 14:30 UTC и сменой терминала D на E
  Тогда открыт сбой типа "задержка" по времени события источника
  И смена терминала зарегистрирована как информационное изменение
```

**AC-DET-02-1**

```
Сценарий: Стыковка разрушена при обоих выполняемых рейсах
  Дано стыковка с плановым запасом 90 минут при MCT 60 минут
  Когда прилёт первого сегмента задержан на 45 минут
  Тогда открыт сбой типа "misconnect"
  И оба сегмента остаются выполняемыми
```

**AC-DET-03-1**

```
Сценарий: Статус после применённого решения открывает повторный сбой
  Дано по сбою выпущено перебронирование на рейс SU5678
  Когда принят статус об отмене рейса SU5678
  Тогда открыт новый сбой, связанный с исходным как повторный
```

## IMP. Оценка влияния

**AC-IMP-01-1**

```
Сценарий: Определены затронутые элементы, участники и класс влияния
  Дано поездка с тремя участниками, план содержит стыковочный сегмент, трансфер и заезд в отель
  И у двоих участников бронирования на сбойный сегмент
  Когда открыт сбой с задержкой 4 часа
  Тогда в оценке влияния перечислены затронутые элементы плана и оба участника поимённо
  И сбою присвоен класс влияния "план неисполним", сопоставление выполнено в UTC
```

**AC-IMP-02-1**

```
Сценарий: Невозвратная активность выделена с суммой потерь
  Дано в плане есть оплаченная невозвратная активность
  Когда она попадает в перечень затронутых элементов
  Тогда она помечена как невозвратная с указанием суммы потерь
```

## ALT. Подбор альтернатив

**AC-ALT-01-1**

```
Сценарий: Подбор в горизонте и порядок ранжирования
  Дано отменён сегмент по маршруту Москва — Токио при горизонте подбора 48 часов
  Когда система подбирает альтернативы
  Тогда все варианты имеют конечной точкой Токио и укладываются в горизонт
  И первым идёт вариант, сохраняющий остальной план и прибывающий раньше
```

**AC-ALT-02-1**

```
Сценарий: Нарушение MCT отклоняет вариант
  Дано альтернатива образует стыковку с запасом 40 минут при MCT 60 минут
  Когда выполняется проверка ограничений
  Тогда результат проверки MCT — "отклонён" с указанием причины
```

**AC-ALT-03-1**

```
Сценарий: Снижение нормы багажа делает вариант годным с условием
  Дано исходный билет включает два места багажа, альтернатива — одно
  Когда выполняется проверка ограничений
  Тогда результат проверки багажа — "годен с условием"
  И указана стоимость доплаты за второе место
```

**AC-ALT-04-1**

```
Сценарий: Отсутствие транзитной визы отклоняет вариант
  Дано гражданство путешественника требует транзитной визы в стране пересадки
  И действующей визы у него нет
  Когда альтернатива предполагает пересадку в этой стране
  Тогда результат проверки визы — "отклонён" по жёсткому ограничению
```

**AC-ALT-05-1**

```
Сценарий: Переход через дату не ломает расчёт стыковки
  Дано альтернатива вылетает 10 июня в 23:40 и прилетает 11 июня в 06:10 в другой таймзоне
  Когда система рассчитывает запас до следующего сегмента
  Тогда расчёт выполнен в UTC без ошибки на сутки
```

**AC-ALT-06-1**

```
Сценарий: Вынужденное перебронирование не порождает разницы тарифа
  Дано рейс отменён по вине перевозчика
  Когда альтернатива предложена в рамках обязательства перевозчика
  Тогда перебронирование помечено как вынужденное и разница тарифа равна нулю
  И вариант вне этого обязательства помечается добровольным с положительной разницей
```

**AC-ALT-07-1**

```
Сценарий: Проверки выполнены до показа, отклонённый вариант недоступен
  Дано вариант отклонён из-за отсутствия транзитной визы
  Когда путешественнику показывается список альтернатив
  Тогда у каждого показанного варианта есть результаты всех проверок с исходом и причиной
  И отклонённого варианта в списке нет, и авто-политика не может его выбрать
```

**AC-ALT-08-1**

```
Сценарий: Годных рейсов нет, предложен перенос активности
  Дано ни одна альтернатива не прошла проверку ограничений
  Когда система формирует предложение
  Тогда предложен перенос затронутой активности в пределах существующего плана
```

## NTF. Уведомления

**AC-NTF-01-1**

```
Сценарий: Уведомление идёт по лестнице каналов и не дублируется
  Дано у путешественника заданы тихие часы и сбой класса "план неисполним"
  Когда система уведомляет о сбое, а затем появляется новая информация по нему
  Тогда уведомление отправлено с канала наивысшего приоритета несмотря на тихие часы
  И новое уведомление заменило предыдущее, активным остаётся одно
```

**AC-NTF-02-1**

```
Сценарий: Переход к следующему каналу по отсутствию подтверждения
  Дано уведомление сдано в push-канал
  Когда подтверждение доставки не получено за отведённый шагу срок
  Тогда уведомление отправлено следующим каналом лестницы
  И статус доставки от провайдера сохранён и связан с уведомлением
```

**AC-NTF-03-1**

```
Сценарий: Состав уведомления
  Дано открыт сбой с подобранными альтернативами
  Когда формируется уведомление
  Тогда в нём указаны событие, затронутые элементы плана, варианты, срок ответа
  И что произойдёт при отсутствии ответа, времена — в локальном времени с таймзоной
```

**AC-NTF-04-1**

```
Сценарий: Оффлайн-путешественник видит решение при входе
  Дано путешественник не отвечал, ack-окно истекло и применена авто-политика
  Когда он открывает приложение
  Тогда он видит сбой, принятое решение и его основание
```

**AC-NTF-05-1**

```
Сценарий: Адресация в поездке с несколькими участниками
  Дано сбой затрагивает двоих из трёх участников поездки
  Когда система публикует сбой и изменение плана
  Тогда организатор видит состояние по каждому затронутому участнику
  И участник видит только своё бронирование
```

## DEC. Принятие решения

**AC-DEC-01-1**

```
Сценарий: Выбор принят от организатора с действующим мандатом
  Дано участник выдал организатору мандат, ack-окно открыто
  Когда организатор выбирает альтернативу за участника
  Тогда выбор принят и зафиксирован как решение по мандату
```

**AC-DEC-02-1**

```
Сценарий: По истечении ack-окна применяется авто-политика
  Дано уведомление сдано в первый канал в 10:00, ack-окно 20 минут
  И заданы авто-политика поездки и авто-политика бронирования
  Когда до 10:20 ответа нет
  Тогда применена авто-политика бронирования
```

**AC-DEC-03-1**

```
Сценарий: Авто-политика не берёт вариант с доплатой без согласия
  Дано единственный годный вариант требует доплаты, согласие плательщика не давалось
  Когда ack-окно истекает
  Тогда авто-политика решение не принимает
  И сбой эскалируется оператору поддержки
```

**AC-DEC-04-1**

```
Сценарий: Эскалация с контекстом сбоя
  Дано провайдер бронирования недоступен после исчерпания попыток
  Когда система не может закрыть сбой автоматически
  Тогда сбой эскалирован оператору поддержки
  И переданы история сбоя, отклонённые варианты и причины отклонения
```

**AC-DEC-05-1**

```
Сценарий: Поздний ответ не отменяет применённое решение
  Дано ack-окно закрыто и решение применено
  Когда путешественник присылает выбор другого варианта
  Тогда применённое решение остаётся в силе
  И система сообщает о нём и предлагает начать новый выбор
```

## REB. Перебронирование

**AC-REB-01-1**

```
Сценарий: Повторный вызов не выпускает второй билет
  Дано выпуск перебронирования по PNR уже выполнен с ключом операции K
  Когда вызов с ключом K повторяется
  Тогда новый билет не выпускается
  И по сбою и бронированию остаётся один выпущенный билет
```

**AC-REB-02-1**

```
Сценарий: Доплата авторизуется до выпуска билета
  Дано выбран вариант с положительной разницей тарифа при добровольной смене рейса
  Когда система выпускает перебронирование
  Тогда билет выпущен только после успешной авторизации доплаты
  И при отрицательной разнице возврат инициирован после успешного выпуска
```

**AC-REB-03-1**

```
Сценарий: Компенсация при неуспехе выпуска
  Дано доплата авторизована и наземная бронь отменена
  Когда провайдер отказал в выпуске билета
  Тогда авторизация доплаты снята, отменённая бронь восстановлена
  И сбой возвращён в состояние выбора альтернативы
```

**AC-REB-04-1**

```
Сценарий: Повторы при недоступности провайдера
  Дано провайдер бронирования не отвечает
  Когда система выпускает перебронирование
  Тогда выполнено до 5 попыток с интервалами 2, 4, 8, 16, 32 секунды
  И отказ перевозчика зафиксирован с причиной, вариант повторно не предлагается
```

## PLN. Обновление плана поездки

**AC-PLN-01-1**

```
Сценарий: План обновлён после выпуска билета
  Дано перебронирование выпущено успешно
  Когда система обновляет план поездки
  Тогда сегменты заменены и временная шкала пересчитана
  И предыдущая версия плана сохранена с указанием сбоя
```

**AC-PLN-02-1**

```
Сценарий: Зависимый элемент перенесён у поставщика
  Дано трансфер стал неисполнимым после переноса рейса
  Когда система обращается к поставщику
  Тогда трансфер перенесён или отменён
  И элемент, отмену которого поставщик не подтвердил, помечен требующим внимания
```

**AC-PLN-03-1**

```
Сценарий: Невозвратный элемент не отменяется автоматически
  Дано в плане есть невозвратная активность, ставшая неисполнимой
  Когда система обновляет план
  Тогда активность не отменена
  И решение по ней запрошено у путешественника отдельно
```

## GRP. Групповые поездки

**AC-GRP-01-1**

```
Сценарий: Роль зависит от поездки, а не от человека
  Дано путешественник организатор в поездке A и участник в поездке B
  Когда система проверяет его права в поездке B
  Тогда права организатора не применяются
```

**AC-GRP-02-1**

```
Сценарий: Отзыв мандата лишает организатора права решать
  Дано участник отозвал мандат до выбора альтернативы
  Когда организатор пытается выбрать вариант за участника
  Тогда выбор отклонён
```

**AC-GRP-03-1**

```
Сценарий: Участник выходит из общего решения до выпуска билета
  Дано организатор выбрал вариант за участника, билет ещё не выпущен
  Когда участник отказывается от общего решения
  Тогда его сбой обрабатывается индивидуально
```

**AC-GRP-04-1**

```
Сценарий: Неуспех у одного участника не откатывает остальных
  Дано общее решение применяется к трём участникам
  Когда выпуск билета для второго участника завершается ошибкой
  Тогда перебронирования первого и третьего остаются в силе
  И сбой второго участника эскалируется
```

## PII. Паспортные данные

**AC-PII-01-1**

```
Сценарий: Паспортные данные отделены от остальных данных
  Дано у путешественника сохранены паспортные данные
  Когда выполняется запрос к основной схеме данных
  Тогда данные документа в ней отсутствуют
  И хранятся в контуре ПДн с отдельными правами доступа
```

**AC-PII-02-1**

```
Сценарий: Наружу отдаётся только маска
  Дано организатор поездки и внешний потребитель запрашивают данные участника
  Когда система отвечает
  Тогда возвращены ссылка на запись и маскированное представление
  И метода, возвращающего полные паспортные данные, во внешнем интерфейсе нет
```

**AC-PII-03-1**

```
Сценарий: Удаление по истечении срока удержания
  Дано поездка завершилась 1 июня и срок удержания составляет 30 суток
  Когда наступает 1 июля
  Тогда запись паспортных данных удалена физически не позднее чем через 24 часа
  И запись попала в отчёт об удалении, расхождений нет
```

**AC-PII-04-1**

```
Сценарий: Обращение к паспортным данным записано в журнал
  Дано оператор поддержки открывает данные документа по сбою
  Когда доступ предоставлен
  Тогда в журнале записаны субъект доступа, время, сбой и обоснование
```

**AC-PII-05-1**

```
Сценарий: Временный доступ оператора прекращается сам
  Дано оператору выдан доступ по сбою с обоснованием
  Когда проходит 60 минут
  Тогда доступ прекращён без действий администратора
  И продление требует нового обоснования
```

**AC-PII-06-1**

```
Сценарий: Провайдеру передан минимальный набор полей
  Дано для выпуска перевозки требуются тип документа, номер, срок действия, дата рождения и имя латиницей
  Когда система вызывает провайдера бронирования
  Тогда переданы только эти поля
  И переданные значения отсутствуют в журналах и трассировках
```

**AC-PII-07-1**

```
Сценарий: Досрочное удаление по требованию путешественника
  Дано у путешественника нет предстоящих поездок
  Когда он требует удалить свои паспортные данные
  Тогда записи удалены физически
```
